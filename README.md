# bun-fixture-migrate

Generates a [bun](https://github.com/uptrace/bun) migration from the diff between two revisions of a
[dbfixture](https://pkg.go.dev/github.com/uptrace/bun/dbfixture) YAML file.

`dbfixture` loads a fixture file into an empty database. That is fine for a fresh checkout and useless
for a deployed one: after the first seed, editing the YAML changes nothing, because nobody re-seeds a
production database. So every change to seed data needs a data migration, and writing those by hand is
tedious and easy to get subtly wrong.

This tool writes it. It diffs your fixture file against an older git revision of itself, matches rows by
a natural key you configure rather than by id, and emits a Go migration with guarded inserts, updates
and deletes. What it cannot do safely it refuses, by name, with a reason.

## Install

```
go get github.com/RELAXccc/bun-fixture-migrate
go install github.com/RELAXccc/bun-fixture-migrate/cmd/bun-fixture-migrate@latest
```

The library needs bun and gopkg.in/yaml.v3, nothing else.

## Example

Say your fixture file holds currencies, subscription plans and the features a plan grants:

```yaml
# fixtures/fixture.yml
- model: Currency
  rows:
    - _id: eur
      id: 1
      code: EUR
      symbol: "€"
- model: Plan
  rows:
    - _id: free
      id: 1
      name: free
      currency_id: '{{ $.Currency.eur.ID }}'
      price_cents: 0
    - _id: team
      id: 2
      name: team
      currency_id: '{{ $.Currency.eur.ID }}'
      price_cents: 2000
- model: Feature
  rows:
    - plan_id: '{{ $.Plan.team.ID }}'
      code: sso
      quota: 1
```

### Configure

Once, next to the fixture file. The tool has no idea which column identifies a row or which column is a
foreign key, so you tell it:

```yaml
# fixture-migrate.yml
fixture: fixtures/fixture.yml
out: internal/migrations
seed_guard_table: plans

models:
  Currency:
    table: currencies
    ref: code          # a reference to a currency names it by its code
    key: [code]        # and two currencies with the same code are the same row
    stable_id: id
  Plan:
    table: plans
    serial: true
    key: [name]
    stable_id: id
    references:
      currency_id: Currency
  Feature:
    table: features
    serial: true
    key: [plan_id, code]
    references:
      plan_id: Plan
    defaults:
      quota: "0"       # what an omitted quota means
```

### Generate

Change the fixture file — raise the team price, add a `pro` plan — and run:

```
$ bun-fixture-migrate -name "plan prices"
Plan: 1 insert, 1 update
wrote internal/migrations/20260921120000_fixture_plan_prices.go
read it, then run your migrations
```

By default it diffs against `HEAD`. Use `-base <ref>` for anything else, or `-old <file>` to skip git.
`-dry-run` prints the file instead of writing it.

### Review

The point of generating a readable file rather than a pile of SQL is that you check it before it runs:

```go
package migrations

import (
	"context"

	"github.com/RELAXccc/bun-fixture-migrate/fixtureapply"
	"github.com/RELAXccc/bun-fixture-migrate/fixturechange"

	"github.com/uptrace/bun"
)

// Generated by bun-fixture-migrate from fixtures/fixture.yml against HEAD.
// 1 insert, 1 update, 0 deletes.
//
// Plan: 1 insert, 1 update
//
// Read it before you run it. Each change is guarded: a row is found by its
// natural key, an update or a delete only touches a row that still holds the
// old values, and an insert only runs when no row with that key exists.
func init() {
	Migrations.MustRegister(func(ctx context.Context, db *bun.DB) error {
		return fixtureapply.Apply(ctx, db, fixtureChanges20260921120000PlanPrices)
	}, func(ctx context.Context, db *bun.DB) error {
		return fixtureapply.Revert(ctx, db, fixtureChanges20260921120000PlanPrices)
	})
}

var fixtureChanges20260921120000PlanPrices = fixturechange.Set{
	Name:           "20260921120000_fixture_plan_prices",
	SeedGuardTable: "plans",
	Tables: fixturechange.Tables{
		"Currency": {Name: "currencies", ID: "id", Key: "code"},
		"Plan":     {Name: "plans", ID: "id", Key: "name", Serial: true},
	},
	Changes: []fixturechange.Change{
		{Model: "Plan", Kind: fixturechange.Insert,
			Key: fixturechange.Values{"name": fixturechange.Lit("pro")},
			New: fixturechange.Values{
				"currency_id": fixturechange.RefTo("Currency", "EUR"),
				"id":          fixturechange.Lit("3"),
				"name":        fixturechange.Lit("pro"),
				"price_cents": fixturechange.Lit("9000"),
			},
		},
		{Model: "Plan", Kind: fixturechange.Update,
			Key: fixturechange.Values{"name": fixturechange.Lit("team")},
			Old: fixturechange.Values{"price_cents": fixturechange.Lit("2000")},
			New: fixturechange.Values{"price_cents": fixturechange.Lit("2500")},
		},
	},
}
```

Note what is not in there: no ids in the `Key` maps, and `currency_id` is a name, not a number. The
migration finds rows by the columns you called the natural key, and resolves `RefTo("Currency", "EUR")`
against the database it runs on. Ids drift between databases; names do not.

### Run

It is an ordinary bun migration, so `migrator.Migrate(ctx)` runs it with the rest of the chain. At run
time `fixtureapply`:

- does nothing at all while `seed_guard_table` is empty, because that database has not been seeded yet
  and `dbfixture` will load the new state by itself;
- resolves every reference to a real id first, and fails the migration if one matches no row or more
  than one;
- inserts only when no row with that natural key exists;
- updates and deletes only while the row still holds the values the old revision had, so an edit
  somebody made by hand survives and a second run is a no-op;
- moves the sequence past any explicit id it wrote into a `serial` table;
- runs everything in one transaction and logs one line per row through `log.Printf` — pass
  `fixtureapply.WithLogger` to send that somewhere else.

`Revert` undoes the set in reverse: the insert becomes a guarded delete, the update swaps its values,
the delete puts the row back.

## Configuration reference

Top level:

| Key | Meaning |
| --- | --- |
| `fixture` | path of the fixture YAML file, relative to the config file |
| `out` | directory the generated files go into |
| `package` | Go package name of that directory, default `migrations` |
| `migrator` | the `*migrate.Migrations` variable to register with, default `Migrations` |
| `seed_guard_table` | a table that is never empty in a seeded database; while it is empty the migration does nothing |

Per model, under `models:`. The key is the model name as it appears in the fixture file; every model in
the file must be listed or the tool stops.

| Key | Meaning |
| --- | --- |
| `table` | the SQL table, optionally schema-qualified. Required |
| `id` | primary-key column, default `id`. Never compared, never updated, written on an insert when the row has one |
| `ref` | the column a reference to this model matches on, default `name` |
| `serial` | the id comes from a sequence |
| `key` | the columns that identify a row without its id, default `[ref]` |
| `key_any_of` | groups of mutually exclusive columns; the first one in a group that is set joins the key |
| `stable_id` | a column that survives a rename, usually `id`; without it renames cannot be detected |
| `references` | column to model, for columns holding another row's id |
| `derived` | columns your application recalculates; never compared, never written |
| `ignore` | columns that take no part at all |
| `defaults` | what a column means when the row leaves it out |
| `no_delete` | refuse deletes of this model |

A few details worth knowing:

- References are resolved through the fixture file itself. A `{{ $.Plan.team.ID }}` template, a plain id
  that some row in the file declares, and an explicit `~` all work; anything the file cannot resolve is
  an error rather than a guess.
- A reference column holding `0`, `""` or null points at nothing and stays a literal.
- An omitted column with no entry in `defaults` is "not set". Two not-set columns are equal; a column
  that is set on one side and not on the other is refused, because the tool would have to invent what
  the missing one means. Add it to `defaults` and run again.
- Inserts write what the row spells out plus the `defaults` for the rest, so the row matches what
  `dbfixture` would have loaded.
- Models are processed in the order they appear in the fixture file. Inserts run in that order, deletes
  in reverse, so nothing is written before the row it points at.

## What it refuses

Each of these ends up in the output with the model, the key and a reason, and nothing is written unless
you pass `-allow-partial`. The exit code is 2.

- **Renames.** The same `stable_id` under a different natural key. An insert plus a delete is not a
  rename: rows elsewhere point at the old one, and whatever depends on the name outside the database
  does too. Both halves are dropped, along with every change that points at the renamed row.
- **Renumbered primary keys.** The same natural key under a different `id`. This tool does not renumber
  primary keys.
- **Deletes of a model marked `no_delete`.** Whether the rows pointing at it should cascade, be
  repointed or block the delete is a decision about your data, not something a diff can work out.
- **Rows whose natural key is not unique**, once the group changes. Two rows with the same key cannot be
  told apart by a `WHERE` clause. An unchanged duplicate group costs nothing and is left alone.
- **Columns that appear on one side only** with no configured default.

In every case the answer is the same: write that one migration by hand, then run the tool again.

## Limitations

- PostgreSQL only. The sequence handling and `IS NOT DISTINCT FROM` are written for it.
- Scalar columns only. A mapping or a sequence in the fixture file is an error unless you `ignore` it.
- Only `{{ $.Model.row.Field }}` templates are understood. Any other template is compared as text, so a
  fixture full of `{{ now }}` will produce noise.
- Values travel as text and are bound as parameters, so the database coerces them. That works for
  numbers, booleans, text and null; exotic column types are untested.
- A delete is guarded by the whole old row including its id, so on a database whose ids drifted the
  delete is skipped and says so in the log rather than deleting the wrong row.
- If the fixture id of an inserted row is already taken by a different row, the insert fails on the
  primary key. That is a conflict you have to look at.
- There is no schema knowledge anywhere: column names come from the fixture file and the config, and the
  tool will happily generate a migration for a column that does not exist. The migration fails when it
  runs, not when it is written.

## Tests

`go test ./...` runs the diff, render and validation tests without a database.

The round trip against a real PostgreSQL lives in the `dbtest` module and is skipped unless a DSN is
set. It seeds with the actual `dbfixture`, applies the generated change set and checks the result
matches a database seeded from the new file:

```
podman run --rm -d -p 55433:5432 -e POSTGRES_PASSWORD=pg --name bfm-test postgres:18
cd dbtest
BUN_FIXTURE_MIGRATE_POSTGRES='postgres://postgres:pg@127.0.0.1:55433/postgres?sslmode=disable' go test ./...
podman rm -f bfm-test
```
